1. Objective

Verify that the VWO Login Dashboard provides a secure, reliable, responsive, accessible, and understandable entry point to the VWO platform. Testing will check the stated login and recovery journeys, account access options, session behavior, user-facing validation and feedback, integration handoffs, and measurable performance and availability requirements.

The plan is based solely on the supplied PRD. It is intended to identify deviations from those requirements before release and to provide evidence for release readiness.

PRD targets to verify
  • Login page load time: within 2 seconds on standard connections.
  • Login success rate: target of 95% or higher.
  • Login-experience satisfaction: target of 90% or higher.
  • Service availability: 99.9% uptime target.
  • Login-related support tickets: target reduction of 20%.
  • Security: no successful brute-force or unauthorized access; no unauthorized session hijacking.

Measurement windows, data sources, calculation rules, and baselines for these targets are not specified and require stakeholder confirmation.

2. Scope

In scope

  • Login page presentation, branding, announcements, and light/dark theme choices.
  • Email and password login, input validation, authentication outcomes, loading and success feedback.
  • Remember Me, session lifecycle and configurable timeout behavior.
  • Forgot-password and email-based account recovery, including secure reset-token behavior.
  • Password requirements and strength feedback where presented in the relevant password flow.
  • Optional 2FA, enterprise SSO (including SAML/OAuth), and social identity-provider options when enabled for the test account/environment.
  • Responsive behavior, keyboard operation, screen-reader support, high contrast, and WCAG 2.1 AA assessment.
  • HTTPS enforcement, protected authentication data, rate limiting, and session security.
  • Successful transition to the VWO dashboard and login success/failure analytics events.
  • Performance, concurrency, availability, and geographic behavior against the PRD targets.
  • Registration/free-trial path, login assistance/support handoff, and post-login context preservation as described in the PRD.

Out of scope / conditional

  • Testing the internal functionality of the VWO experimentation, personalization, and analytics products after authentication.
  • Deep functional validation of external identity-provider systems; verify only the VWO handoff and outcome unless separately agreed.
  • Biometric authentication, adaptive authentication, and PWA behavior: listed as future enhancements, not committed current scope.
  • Marketing campaign behavior and onboarding content beyond the login-to-registration and stated post-registration handoff.
  • Formal certification or legal determination of GDPR, CCPA, or enterprise compliance. QA can verify implemented behaviors and provide evidence; compliance approval remains with the responsible stakeholders.
Scope decision required: The PRD mixes current-state features with proposed requirements, optional capabilities, and future enhancements. Confirm which features are implemented and enabled in the release under test. Conditional features will be marked Not Applicable only after product-owner confirmation.

5. Defect Reporting Procedure

  1. Record each deviation from the approved PRD or expected user journey in the team-approved defect tracker (tool: TBD).
  2. Include a concise title, environment/build, affected test ID, preconditions, reproducible steps, expected and actual results, impact, and supporting evidence such as a screenshot or relevant approved log.
  3. Do not attach real credentials, reset tokens, or other sensitive user data to defects.
  4. Assign severity and priority using the project’s agreed definitions; route authentication/security-impacting issues for prompt triage.
  5. Track the defect through triage, fix, retest, and regression. Link the retest result to the original defect.
  6. Provide a periodic status summary to stakeholders; update cadence and recipients are TBD.

Defect tracker, severity/priority definitions, owners, escalation contacts, and communication cadence: TBD by the project team.

6. Test Strategy

  1. Requirement review: Confirm requirement interpretation, feature availability, acceptance thresholds, and ambiguities. Maintain traceability from each PRD capability to the scenarios in this plan.
  2. Test design: Apply equivalence partitioning and boundary-value analysis to email/password inputs and configured timeout/token boundaries; decision tables to combinations of credentials, Remember Me, and enabled authentication factors; state transitions to login, reset, and session lifecycles; and use-case testing to end-to-end user journeys. Use error guessing and exploratory testing for recovery and feedback behavior.
  3. Smoke testing: Verify page availability, essential form behavior, valid login, failure handling, and dashboard transition. If smoke tests fail, report the build as not ready for deeper execution and await a stable build.
  4. Functional and integration testing: Execute the scenarios in Section 3 across enabled capabilities, including registration/support links, identity-provider handoffs, and login analytics.
  5. Accessibility and compatibility: Check keyboard and assistive-technology behavior, contrast, responsive layouts, and the product’s confirmed supported browsers/devices.
  6. Security validation: Verify security requirements in an authorized environment and coordinate any rate-limit or session tests with the environment owner. Validate implementation evidence for storage and compliance claims where black-box checks are insufficient.
  7. Non-functional testing: Measure page-load time, concurrency, geographic behavior, and availability using approved test profiles and measurement windows.
  8. Regression and retesting: Retest fixes and execute regression on impacted authentication, recovery, session, accessibility, integration, and performance behavior.
  9. Exploratory and end-to-end testing: Explore realistic new- and returning-user flows, including error recovery and successful dashboard access.
Safe execution: Performance, rate-limit, and security validation must use authorized test accounts and an approved environment/load profile. Do not direct high-volume or disruptive tests at production without explicit authorization.

9. Entry and Exit Criteria

Requirement analysis

Entry: The PRD and relevant product details are available to QA.

Exit: Requirements are reviewed; testable acceptance criteria, feature status, and open questions are recorded; material ambiguities have owners.

Test design

Entry: Requirement review has started and the login scope is identified.

Exit: Scenarios, priorities, traceability, test data, and environment needs are prepared and approved by the designated stakeholders.

Test execution

Entry: Candidate application is available; required test accounts and environments are accessible; smoke test passes; test cases and execution rules are approved.

Exit: Planned cases are executed or explicitly dispositioned; results and defects are recorded; critical authentication/security failures are resolved or formally accepted; target results are documented.

Test closure

Entry: Execution and retesting are complete or stopped by an agreed release decision; defect and test reports are available.

Exit: Test summary, residual risks, requirement coverage, unresolved defects, and release recommendation are reviewed by the responsible stakeholders.

Release-target interpretation: Numerical targets (95% login success, 90% satisfaction, 20% support-ticket reduction, 99.9% uptime, and under-2-second page load) need agreed measurement periods, sample sizes, baselines, and data sources before they can be used as objective pass/fail gates.

10. Test Execution and Closure

Execution approach

  • Run smoke checks on each candidate build before in-depth validation.
  • Execute high-priority login, recovery, and session cases first, followed by enabled optional identity flows, UX/accessibility, integrations, and non-functional checks.
  • Record each result as Pass, Fail, Blocked, or Not Applicable, with evidence and linked defect where appropriate.
  • Repeat impacted tests after fixes; run the agreed regression set before closure.
  • Report blockers and security-impacting failures promptly through the agreed escalation path.

Closure summary content

Report build/environment, execution totals by result and priority, requirement coverage, defects by agreed severity, retest/regression status, performance/security/accessibility outcomes, unmet targets, accepted risks, and the release recommendation.
